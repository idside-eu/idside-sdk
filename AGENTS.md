# Repository instructions

- Keep all tracked code, comments, documentation and commit messages in English.
- Do not commit, push or publish unless explicitly requested. Commit messages
  must not mention assistant tooling or add automated co-author attribution.
- Python commands run in `packages/python`: `uv sync --all-extras`,
  `uv run pytest`, `uv run ruff check .`, `uv run ruff format --check .`,
  `uv run mypy`, `uv run bandit -c pyproject.toml -r src`.
- Node commands run in `packages/node`: `npm ci`, `npm run typecheck`,
  `npm test`, `npm run build`. Tests require Node 24; package smoke tests also
  run on the declared consumer floor, Node 22.12.
- Cross-package checks run from the repository root:
  `scripts/check_version_parity.sh`, `scripts/check_sdk_parity.sh`,
  `scripts/check_publishable.sh`, `scripts/check_docs_examples.sh`.
- Preserve fail-closed behavior: caller-supplied proof headers never authorize
  a provider call, malformed authorization responses never reach the provider,
  and incomplete installation of transport guards must fail explicitly.
  Bind internal provenance to the wrapped client, token and sending endpoint;
  preserve legitimate retries and roll back only patches owned by a failed wrap.
  Validate all ten required authorization fields. Keep `source` and
  `legal_basis` opaque printable metadata; see `docs/versioning.md`.
- Prompt cleaning is one engine written twice (`idside/_cleaning/`,
  `src/cleaning/`): `packages/descriptors/content-rules.json` is its single
  catalogue (byte-identical copies in both SDKs) and
  `testdata/content-cleaning-vectors.json`, generated by
  `build_content_vectors.py` from hand-written expectations, holds both to the
  same output. Patterns stay in the portable, linear-time subset; never log,
  raise or report a matched value; no tracked file holds a whole secret-shaped
  string (split it, as the vectors do). A detector never counts a value it
  masked only in part: a character a value class takes must also stand in that
  pattern's boundaries. A match whose value group took no part is context that
  rules a value out (a version word before four numbers): both engines skip it
  whole. A `block_only` pattern runs only when its detector blocks: under Mask
  what it alone finds is neither masked nor counted (a private key's BEGIN line
  quoted in prose), since every placeholder written is a value counted. What
  no portable pattern reads in linear time is a named check of the engine
  (`followed_by`, written alike in both SDKs: `material.py` / `material.ts`),
  where two neighbouring parts of a pattern would take the same characters
  (a backtracking matcher retries every split). Each
  detector's `description` says what it reads, never more.
  `test_content_whole_values.py` / `contentWholeValues.test.ts` hold the rule
  that matters most: a counted value leaves no run of four of its characters
  in the output, whatever surrounds it, and one in a neutral context is
  counted at all (a context skipped is a failure). A guard never rejects a
  valid value for what follows it: what follows after a separator is not part
  of it, and what carries it on is taken with it. A value that runs on (to its
  delimiter, to the end of the text) is followed by the engine (`extend`, a
  bounded expression applied again and again), never by a pattern whose
  nested repetitions grow with the text: the catalogue lint refuses any above
  65,536, as JavaScript keeps a frame per repetition. Every boundary before a
  value accepts an escape written in two characters (`\\[nrt]`). Findings that
  overlap are masked as one. `test_content_oracle.py` / `contentOracle.test.ts`
  clean a generated corpus with the frozen engine of
  `testdata/reference-engine/` (never edited, never shipped) and fail on any
  character it masked that the engine no longer masks, except under a named
  exclusion of `testdata/content-oracle.json`: a pattern change runs it before
  anything else.
  `testdata/content-entry-vectors.json` (from `build_entry_vectors.py`) holds
  which custom entries a policy may carry; the ID Side cloud reads it too, so a
  change to how either SDK compiles an entry changes that file first.
- The cleaning policy is applied only once it checks out, and fail-closed
  otherwise: its `kid` must start with `content-policy-` (the cloud names each
  key after its purpose, so an ACT key never signs a policy), checked before
  the key set is read. Python verifies ES256 with `cryptography` when installed
  and with `_p256.py` otherwise, after checking the signature length and the
  curve point itself so both judge the same inputs; `check_publishable.sh`
  proves a wheel without the `[verify]` extra verifies and applies a signed
  policy. Every wrapped client asks `/v1/content-policy`, even when nothing is
  enabled: a call that cleans nothing still sends no `content_policy` field.
  While a valid policy is held, the cloud is asked at most once every ten
  seconds, whatever the last attempt gave; once none is held, every call asks.
  A wrapped client has one fetch of the policy and of the key set in flight
  (a lock and a shared future in Python, its own task in asyncio, a shared
  promise in Node): concurrent calls wait for it and share its result, a
  failure included, which is never kept. A policy held stops at the earlier of
  its `exp` on the wall clock and `exp - iat` after its reception on the
  monotonic clock: never one bound without the other.
  Dates are checked last, so a policy refused for them is one whose clock is out
  of step, and the message says so in the same words in both SDKs.
- Keep Python/Node behavior and bundled descriptors aligned. Test real provider
  client objects with mocked networking; do not send live provider requests as
  an incidental part of a local test.
- Preserve historical request hashes. Update public contracts when changing
  verification options, response validation or compatibility behavior.
- Publication is manual from the matching `v<VERSION>` tag and waits for the
  complete reusable CI workflow on the same commit. See `RELEASING.md` for
  registry setup and repository protections.

- Integration docs use `https://sdk.idside.eu`, the SDK default, and the
  registry installs, bare first (`pip install idside`, `npm install @idside/sdk`:
  the SDK wraps the provider client a reader already has), then the
  starting-from-nothing forms (`pip install 'idside[openai]'`,
  `npm install @idside/sdk openai`).
  `IDSIDE_BASE_URL` is for a local or staging cloud: the origin alone, without
  `/v1` or `/widget`. Naming the end user is optional: a call with no
  identity sends no identity field, and the API key is the proof's subject
  (`binding: api_key`; the answer's binding must be the identity sent —
  `user_id`, `ubt`, or `api_key` for none — and nothing else). An identity that
  is present but names nobody stays a `MissingIdentityError`, and so does a call
  naming nobody made from inside an enforced call in progress (a provider
  helper re-entering without the permit); two stay a `ConflictingIdentityError`.
  An argument spelled like `user_id`/`ubt` but not exactly (`userId`, `USER_ID`,
  `Ubt`: equal once case and separators are stripped) is an
  `UnenforceableOptionError` before the identity is read, in both SDKs. Strict
  visitor apps need a UBT bound to the same server session; never fall back to
  `user_id` or to naming nobody.
